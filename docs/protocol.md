# Протокол Clipvey v1

Clipvey синхронизирует текст буфера обмена между Mac и Windows в локальной сети. Оба приложения равноправны. Каждое:
- слушает TCP;
- объявляет себя через mDNS;
- ищет другие устройства;
- умеет подключаться само.

Роли задаются для каждого соединения отдельно:
- **I (initiator)** — сторона, которая подключилась;
- **R (responder)** — сторона, которая приняла соединение.

Реализации на Swift (Mac) и C# (Windows) обязаны совпадать до байта во всём, что описано ниже.

## Транспорт и поиск

- **TCP.** Порт по умолчанию `48620`. Если он занят, берётся любой свободный, а фактический порт публикуется через mDNS.
- **mDNS / DNS-SD.** Тип службы `_clipvey._tcp`, домен `local`. Имя экземпляра — имя устройства. TXT-записи:
  - `id=<deviceId>`;
  - `v=1`;
  - `pair=1`, пока открыт режим связывания, иначе `pair=0`;
  - `os` и `form` — необязательные, см. «Тип устройства».
- **Как объявляют себя стороны.** Mac — через системный Bonjour (`NWListener`). Windows — собственным mDNS-ответчиком на UDP 5353, который делит порт с системной службой.
- **Как ищут.** Однократными (legacy unicast) запросами по RFC 6762 §6.7 с эфемерного порта на `224.0.0.251:5353`, отдельно с каждого IPv4-интерфейса. На Mac вместо этого используется `NWBrowser`.
- **Запасной адрес.** Последний адрес, с которым удалось соединиться, сохраняется и пробуется первым.
- **Кадр.** `u32` длина в big-endian, затем нагрузка. Допустимая длина — от 1 до 4 МиБ (4 194 304 байта).
  - До установки шифрования нагрузка — объект JSON в UTF-8.
  - После — шифротекст AES-256-GCM, за которым идёт 16-байтный тег.

## Ключи и кодировки

- Ключ устройства — долговременная пара P-256.
  - Публичный ключ передаётся в формате X9.63 без сжатия: 65 байт, `0x04 ‖ X ‖ Y`.
  - `deviceId` — первые 16 байт `SHA-256(публичный ключ)` в виде hex строчными буквами (32 символа).
- Двоичные поля в JSON — base64 (RFC 4648 §4, с `=`-дополнением).
- Строки-разделители доменов — ASCII-байты без завершающего нуля:
  - `"Clipvey v1 commit"`;
  - `"Clipvey v1 code"`;
  - `"Clipvey v1 session"`;
  - `"Clipvey v1 keys"`.
- `‖` означает конкатенацию. Все поля в ней фиксированной длины: ключи — 65 байт, одноразовые числа (nonce) — 32 байта.

## Связывание

Пользователь нажимает «Связать» на обоих устройствах. Оба переходят в режим связывания (`pair=1`) и показывают список других устройств, которые тоже в этом режиме.

На одном из них пользователь выбирает второе. Выбравшее устройство подключается и становится I, второе становится R:
- **R** показывает код и имя I;
- **I** просит ввести этот код.

Каждый шаг — отдельный кадр:

| № | Направление | Сообщение |
|---|---|---|
| 1 | I → R | `{"t":"pair_hello","v":1,"name":NAME_I,"key":b64(PK_I),"os":…,"form":…}` |
| 2 | R → I | `{"t":"pair_commit","name":NAME_R,"key":b64(PK_R),"commit":b64(C),"os":…,"form":…}` |
| 3 | I → R | `{"t":"pair_nonce","nonce":b64(N_I)}` |
| 4 | R → I | `{"t":"pair_reveal","nonce":b64(N_R)}` |
| 5 | I → R | `{"t":"pair_verified"}` или `{"t":"pair_abort","reason":"code"\|"cancel"}` |
| 6 | R → I | `{"t":"pair_done"}` или `{"t":"pair_abort","reason":"cancel"}` |

Что вычисляется на каждом шаге:
- **Шаг 2.** `N_R` — 32 случайных байта. Обязательство `C = SHA-256("Clipvey v1 commit" ‖ PK_R ‖ PK_I ‖ N_R)`.
- **Шаг 3.** `N_I` — 32 случайных байта. I отправляет его только после того, как получил `C`.
- **Шаг 4.** I пересчитывает `C` и сравнивает с полученным. Если не совпало — `pair_abort` и разрыв.
- **Код.** Обе стороны вычисляют:

  ```
  h    = SHA-256("Clipvey v1 code" ‖ PK_I ‖ PK_R ‖ N_I ‖ N_R)
  code = (big-endian uint32 из h[0..4]) mod 1 000 000
  ```

  Код показывается как 6 цифр с ведущими нулями.
- **Шаг 5.** I шлёт `pair_verified`, только если введённый пользователем код совпал со своим.
- **Шаг 6.** R шлёт `pair_done` только после того, как получил `pair_verified` и пользователь нажал на R «Готово». После шага 6 соединение закрывается.
- **Что сохраняется.** Каждая сторона сохраняет `(deviceId, имя, публичный ключ)` второй.

Правила связывания:
- **Только в режиме связывания.** R принимает `pair_hello`, только если на нём открыт режим связывания. Иначе он отвечает `{"t":"error","reason":"not_pairing"}`.
- **Один сеанс за раз.** Устройство участвует не больше чем в одном сеансе связывания, в любой роли. Остальным отвечает `{"t":"error","reason":"busy"}`.
- **Срок жизни.** Режим связывания и сеанс длятся не дольше 120 секунд. После ошибки или отмены нужен новый код.

Почему это безопасно:
- Код не передаётся по сети.
- Обязательство `C` не даёт злоумышленнику посередине подобрать одноразовые числа так, чтобы коды совпали. Остаётся шанс 1 : 1 000 000 за одну попытку.
- Клик «Готово» на R не даёт постороннему устройству связаться с R вместо того, за которым сидит пользователь.

## Сеанс между связанными устройствами

1. I → R: `{"t":"hello","v":1,"id":deviceId_I,"eph":b64(E_I)}`, где `E_I` — эфемерный публичный ключ P-256.
2. Если `deviceId_I` не связан с R, R отвечает `{"t":"error","reason":"unknown_device"}` и закрывает соединение.
3. R → I: `{"t":"hello_ack","id":deviceId_R,"eph":b64(E_R)}`. Если `deviceId_R` не тот, к которому подключался I, I закрывает соединение.
4. Обе стороны вычисляют три значения ECDH (сырой общий секрет, 32 байта):

   | Значение | Считает I | Считает R |
   |---|---|---|
   | `dh1` | `ECDH(e_I, E_R)` | `ECDH(e_R, E_I)` |
   | `dh2` | `ECDH(s_I, E_R)` | `ECDH(e_R, PK_I)` |
   | `dh3` | `ECDH(e_I, PK_R)` | `ECDH(s_R, E_I)` |

   Затем:

   ```
   th    = SHA-256("Clipvey v1 session" ‖ PK_I ‖ PK_R ‖ E_I ‖ E_R)
   okm   = HKDF-SHA256(ikm = dh1 ‖ dh2 ‖ dh3, salt = th, info = "Clipvey v1 keys", L = 64)
   k_IR  = okm[0..32]    ключ направления I → R
   k_RI  = okm[32..64]   ключ направления R → I
   ```

5. Шифрованный кадр:
   - `nonce = 00 00 00 00 ‖ big-endian uint64 счётчик`;
   - счётчик свой для каждого направления, начинается с 0;
   - AAD пустой;
   - нагрузка — `ciphertext ‖ tag`.

   Любая ошибка расшифровки означает разрыв соединения.
6. Первое шифрованное сообщение в каждую сторону — `{"t":"ready","name":NAME,"os":…,"form":…,"caps":[…]}`. Любое другое первое сообщение означает разрыв. Поля `os`, `form` и `caps` необязательные (см. «Тип устройства» и «Картинки»).

Шифрованные сообщения:

| Сообщение | Назначение |
|---|---|
| `{"t":"clip","id":ID,"origin":deviceId,"hops":N,"text":"…"}` | Текст буфера обмена (см. «Несколько устройств») |
| `{"t":"info","name":NAME,"os":…,"form":…,"caps":[…]}` | Изменились имя или возможности устройства (см. «Изменения в сеансе») |
| `blob_start`, `blob_chunk`, `blob_end` | Картинка (см. «Картинки») |
| `{"t":"ping"}` | Каждая сторона отправляет раз в 15 с |
| `{"t":"pong"}` | Ответ на `ping` |

Поля `clip`:
- `id` — 16 случайных байт в hex, 32 символа;
- `origin` — `deviceId` устройства, на котором текст скопировали;
- `hops` — сколько раз фрагмент уже пересылали, у исходного устройства `0`;
- `text` — не больше 1 МиБ в UTF-8, переводы строк `\n`.

Если по соединению 45 секунд не приходит ни одного кадра, оно считается мёртвым.

## Несколько устройств

Связь между устройствами попарная, связанных устройств может быть сколько угодно. Текст доходит до всех устройств, между которыми есть цепочка связей:

1. Устройство, на котором скопировали текст, отправляет `clip` с новым `id` и `hops=0` всем подключённым включённым устройствам.
2. Получатель проверяет `id` по списку последних 500 полученных. Если такой `id` уже был, фрагмент отбрасывается.
3. Если фрагмент новый, получатель кладёт текст в буфер обмена. Затем пересылает его с `hops+1` всем своим подключённым включённым устройствам, кроме отправителя и устройства `origin`.
4. При `hops ≥ 8` фрагмент дальше не пересылается.

Поэтому новое устройство достаточно связать с любым одним из уже связанных. Если связать больше пар, доставка станет надёжнее (например, когда промежуточное устройство выключено), а дубли всё равно отбрасываются по `id`.

**Выключенные устройства.** Любое связанное устройство можно выключить, не разрывая связь.
- С выключенным устройством не устанавливается сеанс, и ему не пересылаются фрагменты.
- На `hello` от выключенного устройства R отвечает `{"t":"error","reason":"disabled"}` и закрывает соединение.
- Сторона, получившая `disabled`, повторяет попытки не чаще раза в 30 секунд.

## Совместимость версий

Версия протокола остаётся `1`. Всё, что добавлено после Clipvey 0.1.0, необязательно, и старые версии это переносят:
- лишние поля в известных сообщениях и лишние ключи TXT игнорируются;
- сообщение с неизвестным `t` внутри сеанса записывается в журнал и пропускается, сеанс не рвётся.

Отсюда правила для новых версий:
- не требовать новых полей: если поля нет, брать значение по умолчанию;
- не слать новых сообщений тому, кто не заявил нужную возможность в `caps`, если сообщение большое или без него нельзя обойтись (картинки);
- `info` можно слать всем: старая версия его пропустит.

## Тип устройства

Необязательные поля в TXT, `pair_hello`, `pair_commit`, `ready` и `info`:
- `os` — `mac`, `windows` или `linux`;
- `form` — `laptop` или `desktop`.

Если поля нет или значение незнакомое, устройство показывается общим значком. Тип нужен только для значков в интерфейсе.

## Изменения в сеансе

`{"t":"info","name":NAME,"os":…,"form":…,"caps":[…]}` — устройство сообщает, что изменилось его имя или набор возможностей (например, пользователь выключил «Передавать картинки»). Шлётся в любой момент после `ready`, всем открытым сеансам. Все поля кроме `t` необязательные. Отсутствующее поле значит «не изменилось», а не «пусто»: `caps` без картинок — это `"caps":[]`.

Получатель:
- обновляет сохранённое имя устройства (как по `ready`);
- заменяет известный набор `caps` этого сеанса.

При смене своего имени устройство также обновляет TXT и имя экземпляра mDNS.

## Картинки

Возможность `image` в `caps`: устройство принимает картинки. Устройство заявляет её, только если у него включено «Передавать картинки». Картинки шлются только тем сеансам, у которых последний известный `caps` содержит `image`.

Картинка передаётся тремя видами сообщений:

| Сообщение | Поля |
|---|---|
| `{"t":"blob_start","id":ID,"origin":deviceId,"hops":N,"kind":"image","mime":MIME,"size":N,"sha256":b64(H)}` | `id`, `origin`, `hops` — как у `clip`. `mime` — `image/png` или `image/jpeg`. `size` — длина данных в байтах, от 1 до 20 971 520 (20 МиБ). `sha256` — хеш всех данных, 32 байта в base64. |
| `{"t":"blob_chunk","id":ID,"seq":N,"data":b64(…)}` | `seq` — номер куска с 0. Каждый кусок, кроме последнего, ровно 524 288 байт (512 КиБ) до кодирования, последний — от 1 до 524 288. |
| `{"t":"blob_end","id":ID}` | Конец картинки. |

Отправитель:
- шлёт куски по порядку сразу за `blob_start` и завершает `blob_end`;
- в одном сеансе передаёт не больше одной картинки одновременно; между её кадрами могут идти `clip`, `info`, `ping` и `pong`;
- исходное устройство шлёт картинку с `hops=0` и новым `id` из того же пространства, что и `id` у `clip`.

Получатель:
- **Повтор.** Если `id` из `blob_start` уже есть в списке последних 500 `id` (общем с `clip`), вся картинка пропускается до `blob_end`.
- **Отказ без разрыва.** Если `kind` не `image`, `mime` незнакомый, `size` вне допустимого, или «Передавать картинки» выключено, картинка пропускается до `blob_end`. Сеанс не рвётся.
- **Проверка.** Кусок с не тем `id` или `seq`, превышение `size`, нехватка данных к `blob_end` или несовпадение `sha256` — картинка отбрасывается и пишется в журнал, сеанс продолжается. Новый `blob_start`, пока предыдущая картинка не закончена, отбрасывает предыдущую.
- **Готово.** Только после `blob_end` с совпавшими `size` и `sha256` `id` заносится в список последних, картинка кладётся в буфер обмена и пересылается с `hops+1` (если `hops+1 < 8`) всем подключённым включённым устройствам с `image` в `caps`, кроме отправителя и `origin`.

Устройство с выключенными картинками их не заявляет, поэтому не получает и не пересылает. Цепочка из трёх устройств передаёт картинки, только если на промежуточном они включены.

## Кто подключается

С каждым связанным устройством держится не больше одного сеанса:
- **Кто начинает.** Если сеанса нет, первым подключается устройство с меньшим `deviceId` (при сравнении строк). Второе пробует подключиться само, только если сеанс не появился за 5 секунд. Это нужно на случай, когда входящие соединения к первому заблокированы брандмауэром.
- **Если сеансов получилось два.** Такое бывает, когда обе стороны подключились одновременно. Обе стороны оставляют тот, у которого I — устройство с меньшим `deviceId`, а второй закрывают. Решение детерминированное, поэтому стороны закрывают один и тот же сеанс.
- **Переподключение.** После обрыва переподключение идёт по тем же правилам.

## Поведение сторон (не часть протокола)

- **Переводы строк.** Windows переводит `\r\n` ↔ `\n`.
- **Картинки в буфере.**
  - Mac отправляет PNG как `image/png`. Скриншоты и TIFF переводит в PNG, HEIC — в JPEG. В буфер пишет PNG (и JPEG как есть).
  - Windows отправляет формат `PNG`, а если его нет — `CF_DIBV5` или `CF_DIB`, переведённый в PNG. В буфер пишет `PNG` и `CF_DIB`, чтобы вставка работала и в старых программах.
  - Картинки больше 20 МиБ не отправляются.
- **Защита от зацикливания.** Сторона, записавшая в буфер полученный текст или картинку, помечает запись своим маркером и не отправляет её обратно.
  - На Mac маркер — тип `io.github.lovipomidorku.clipvey.remote`.
  - На Windows — формат `ClipveyRemote`.
- **Пароли не передаются.** Не отправляется текст, помеченный как секретный:
  - на Mac — типы `org.nspasteboard.ConcealedType` и `org.nspasteboard.TransientType`;
  - на Windows — форматы `ExcludeClipboardContentFromMonitorProcessing` и `Clipboard Viewer Ignore`.
